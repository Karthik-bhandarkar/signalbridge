Case study · Incident response platform

A flood of alerts becomes one incident on-call can act on.

SignalBridge is a webhook pipeline for engineering teams. It verifies every alert, removes the duplicates, groups related signals into a single incident, and keeps a timeline of who did what. Designed and built by Karthik Bhandarkar.

The problem

On-call drowns in alerts that describe the same failure.

One slow endpoint can produce dozens of near-identical notifications. The person on call spends the first ten minutes of an incident closing duplicates instead of fixing the cause.

01
Retries look like new failures

A monitoring tool retries four times. Four pages go out for one problem.

02
Nobody checks who sent the alert

An unsigned or spoofed webhook is treated exactly like a real outage.

03
The history disappears

When the page is closed, so is the record of what happened and who did what.

The solution

One endpoint in. One incident out.

Every alert goes through a single pipeline with a recorded outcome at each stage. Nothing is inferred and nothing is silently dropped.

The design rule: a stage either succeeds, is skipped with a reason, or fails loudly. All three are written to a ledger, so an incident can be explained afterwards.
  • Verified. Each delivery is checked against its source's signing secret before it touches the database.
  • Deduplicated. A repeat delivery is acknowledged and recorded, then stopped. It never opens a second incident.
  • Correlated. Alerts sharing a service and event type join the open incident inside a 30-minute window.
  • Explainable. Severity rises from signal count and the worst severity seen. Every change is written to the timeline.
  • Recoverable. Raw payloads are kept with the event, so an incident can be reviewed byte for byte.
How it works

Five stages, each one visible in the app.

You can follow a single delivery from the request to the incident it joins.

1

Receive

One endpoint per source. The raw body is read before anything is parsed.

POST /api/v1/webhooks/:source
2

Verify

The signature is recomputed over the exact bytes and compared in constant time.

HMAC-SHA256 → 202 or 401
3

Deduplicate

A unique idempotency key decides whether this delivery has work to do.

unique index on dedupe_key
4

Correlate

Service and event type produce a fingerprint. Open incidents absorb it.

30-minute correlation window
5

Respond

An operator acknowledges, adds a note or resolves. The timeline keeps it.

append-only incident_timeline
Key features

Six things on-call actually feels.

Each one removes a specific kind of noise, not noise in general.

Signed ingest

Per-source secrets, compared in constant time. A tampered or unsigned delivery is rejected before storage.

Duplicate suppression

An idempotency key, unique index behind it. Replays return 200 and leave no downstream effects.

Correlation window

Related alerts join one incident. Resolved incidents do not absorb new signals, so a relapse opens fresh.

Stage ledger

Every stage writes its outcome, duration and reason to a task table. Failures are visible, not swallowed.

Payload kept with the event

The original JSON is stored alongside the delivery, with its archive key and byte count.

Operator timeline

Acknowledge, note, resolve, reopen. Each action is attributed and appended, never edited.

My role

I designed and built the whole thing, and here is the boundary.

Solo project. No team, no inherited codebase. The honest scope matters more than a long list.

What I built

  • Data model: sources, webhook events, incidents, timeline entries, task runs and operators.
  • Ingest pipeline: signature check, idempotency, normalisation, fingerprinting, escalation, archival.
  • API routes for ingest, events, incidents, metrics and health, with a per-stage trace in the response.
  • Operations console: overview, incident detail, event stream, system health, operator actions.
  • Demo seeding so a reviewer lands on a working, populated app rather than an empty table.
  • This case study page and a browser script that checks the console flows.

What I deliberately did not do

  • No external queue. Stages run inline and are recorded, so the same logic can move to a worker later.
  • No object storage. Payloads are kept in PostgreSQL JSONB, and the page says so instead of implying S3.
  • No live PagerDuty or Datadog accounts. Sources are registered locally and signed with their own secrets.
  • No production SLA claim. This is a demo environment, labelled as one in the footer.
